# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. Read it before making changes.

## What this is

Reel Radar: a single-user Next.js 16 (App Router) app for movie/TV discovery, watch tracking, recommendations, taste analytics, a daily todo planner, and a money tracker. Data comes from the TMDB v3 API. State lives in the browser (`localStorage`) and syncs to Turso (libSQL), or to `data/*.json` locally when Turso isn't configured.

Stack: Next.js 16, React 19, TypeScript (strict), Tailwind 3, Vitest 4, `@libsql/client`.

## Environment

Copy `.env.example` to `.env.local`. Never commit `.env.local` or print its values.

| Var | Required | Purpose |
|---|---|---|
| `TMDB_API_KEY` | yes | Every TMDB call goes through the server; it's never exposed to the client |
| `APP_USERNAME`, `APP_PASSWORD` | yes | Single-user login credentials |
| `AUTH_SECRET` | yes | HMAC key for the session cookie |
| `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN` | no | Turns on Turso storage; without the URL, storage falls back to `data/` |
| `MONEY_ENCRYPTION_KEY` | for Money | 32 bytes, base64. `docStore` encrypts `money-*` docs with it; money reads and writes fail without it |
| `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, `PUSH_CRON_SECRET` | no | Closed-app reminders. The public key reaches the browser through `GET /api/push` behind the login; don't make any of these `NEXT_PUBLIC_` |
| `MONEY_MY_NAMES`, `MONEY_FAMILY` | no | Starter family for Money (`lib/moneyFamily.ts`), served by `api/money/family` and added once by `seedFamily()`. Keeps real names out of the public repo; never make them `NEXT_PUBLIC_` (static bundles aren't behind the login) |
| `BLOB_READ_WRITE_TOKEN` | scripts only | For the scripts that read or clean up old Vercel Blob data. The app doesn't use it |

## Keep away from live data

`.env.local` holds the real Turso credentials, and the owner often has their own `next dev` running from this repo against the live database.

- Start any dev server or script you run with the store turned off, on a different port: `TURSO_DATABASE_URL= npx next dev -p 3001`. An empty shell variable takes precedence over `.env.local`, and `docStore` then falls back to `data/`.
- Remember that edits to sync, storage or `docStore` code hot-reload into the owner's running server and their open tabs, so they can reach live data before any deploy.
- Ask before running `scripts/*.ts` without `--dry-run` or listing mode, or before anything else that writes to or deletes from Turso.
- When changing sync or storage, count the database reads and writes and the function calls the change adds (see "Free-tier usage and performance").

## Conventions and invariants

- **Title identity**: a title is identified by `keyOf(t)` → `"movie:123"` / `"tv:123"`. A TMDB id alone isn't unique across media types.
- **State shape** (`State` in `lib/storage.ts`): `watched`, `watchlist` (full `Title` objects), and `displayed`, `shown`, `dismissed` (key strings). If you add a field, update all of these together in `lib/syncDocs.ts`: `empty()`, `libraryOf()`/`historyOf()` and `mergeLibrary()`/`mergeHistory()`, plus import/export.
- **localStorage key** `reel-radar-v1` holds user data. Don't rename it or change the shape in ways that break existing saved data. Make migrations additive.
- **Merging** (`mergeStates`) unions watched seasons. Keep it idempotent, because import and sync both depend on it.
- **Sync** (`api/sync`, `lib/docStore.ts`, `lib/sync.ts`): data is split into docs (`library`, `history`, `planner-YYYY-MM`, `planner-daily`, `planner-log`, `planner-lists`, `planner-settings`, `planner-bin`, `money-YYYY-MM`, `money-settings`, `books`, `piano-settings`, `piano-YYYY-MM`, `piano-song-<12 hex>`; the allowlist is `DOC_KEY`). Keep these properties:
  - Reads send the client's etag, and an unchanged doc comes back without its body. A failed read must surface as an error, never as "missing", or the client pushes over the doc.
  - Writes are conditional (`UPDATE ... WHERE etag = ?`). A push with no etag only creates a doc (`writeDoc(key, data, null)`), so a device that never pulled it can't replace it. A 409 carries the server copy; the client merges and retries.
  - Pushes are batched through `markDirty()`; don't `fetch` the sync route from features directly. A sync must not write back what it just read.
  - Merges are three-way against the stored base (`merge3`), so deletes carry across devices. Planner items carry `updatedAt`; daily copies use the fixed id `<dailyId>:<date>`.
  - Without `TURSO_DATABASE_URL` everything falls back to `data/<doc>.json`.
  - `money-*` docs are encrypted at rest in `docStore` (`seal`/`unseal`: AES-256-GCM, `enc:v1:<iv>:<ciphertext+tag>`, the doc key as AAD), in Turso and `data/` alike. Etags hash the stored (encrypted) text. Never add a path that stores them unsealed or falls back to plain text when the key is missing. Plain legacy docs are sealed on read (the read query returns their body even for a matching etag). Tests set the key with `vi.stubEnv("MONEY_ENCRYPTION_KEY", ...)`.
  - `readDoc`/`writeDoc` count every call per half hour (`flushUsage()` saves the counts to the `usage` table, or `data/usage.json`; `/api/usage` serves them to the stats page). Any new code path that queries the `docs` table must go through them so it is counted.
- **Media** (list photos and voice notes): one `media-<id>` doc each, through `readDoc`/`writeDoc`/`deleteDoc` in `api/media/[id]`, never `/api/sync` (they stay out of `DOC_KEY` and out of `localStorage`). Ids are random and files are never rewritten, so GET answers `private, immutable`. Only the types in `MEDIA_TYPES` are stored or served (no SVG or HTML), up to `MAX_MEDIA_BYTES`. List items keep `MediaRef`s; whoever drops an item, photo or list deletes its media. Links on items go through `cleanLink()` (http/https only) before they reach an `href`. `next.config.mjs` allows `microphone=(self)` for voice notes.
- **Postponing**: `postponeCount()` is the one reader of a todo's `postponed` (tasks older than that field count once if they have `carriedFrom`). `carryOverdueTo()` and `moveTodoToDate()` raise it; a move only counts when an unfinished task leaves today or a past day for a later one, not when future plans are rearranged. Overdue covers one-off tasks only, because every day gets its own daily copy. Todo ids are unique across a month doc: `saveTodos` treats the same id on another day as a move.
- **Bin** (`planner-bin`, `BinItem`): tasks the user deletes (task details, Needs attention's Drop, the review's drop) go through `binTodo()`, and Clear completed bins what it clears; they stay `BIN_DAYS` (7). `deleteTodo()` itself never bins, because moves use it too. `restoreTodo()` takes a task out of the bin, so every Undo also clears its entry. `loadBin()` hides expired entries and the next write drops them. The bin isn't in `plannerKeys`: it's pulled only when More › Bin opens (`syncBin()`), and `restoreFromBin()` pulls the task's month first. The backup leaves it out.
- **Day log streaks**: a tile shows `🔥n` once `streakEnding()` reaches 2. It counts back from the day shown, and an open day doesn't break the run.
- **Deadlines**: a todo's `due` is separate from the day it's planned on, so moving or carrying a task keeps it. Only one-off tasks have one: `addTodo`, `setTodoDue` and `makeTodoDaily` enforce that, and `copyTodoToDate` drops it. `getDueTodos()` feeds the tray, and the page leaves those tasks out of Overdue so each shows once. That tray can hold tasks planned ahead, so `syncTrayPlanner()` pulls next month as well as every past one.
- **Goals**: live in `planner-settings` (no extra doc to read). Todos and daily tasks hold a `goalId`, which each day's copy of a repeat inherits, and `syncDailyFrom` carries a change to later days. A deleted goal's id stays on its tasks and just stops matching. `computeGoalProgress()` is the one place that decides what counts. The percentage covers one-off tasks only, because repeats have no end; every finished copy of a linked repeat counts, including cleared ones (`doneDates`), and missed copies don't.
- **Day log items**: their definitions (`LogItemDef`: a tick or a number, with an order) live in `planner-settings` as `logItems`, merged like tags; built-ins have no entry until changed, so a doc without the field (from an older device) reads as the seven built-ins. A removed item keeps its entry. A day's values are `DayLog.ticks` (`{ at? }`, minutes after midnight, only for a tick made on the day itself) and `DayLog.counts`, written through `setLogTick()`/`setLogCount()`; `updateDayLog()` and the backup import both clean them with `cleanTicks()`/`cleanCounts()`. Ticks stay out of the schedule's Done column and out of search.
- **Search**: the planner's Search pulls everything once on open, then filters this browser's copy, so keep it free of per-keystroke requests. A result opens its day, list item or Goals inside the page. From outside, `/todos?date=YYYY-MM-DD` and `/todos?list=<id>&item=<id>` (or the old `/todos/lists?…`, redirected) open them; the planner clears its parameters so a later reload goes back to today.

- **PDFs in Books** (`lib/pdf.ts`): the type is told from the bytes (`isPdf()`: a `%PDF-` header in the first 1 KB), never the file name, in `addBook()` and `openBook()`. `parsePdf()` returns the same `ParsedBook` as `parseEpub()`, so the player, chapter list, position and sync don't know the difference: a PDF's chapters are the top-level entries of its outline when it has one that points at pages (`outlineStarts()`: entries in page order, unresolvable ones skipped, the first of two on one page kept, text before the first entry an opening chapter titled by page range), otherwise groups of 10 pages titled "Pages 1–10" (a position is chapter plus sentence). Nested outline entries are ignored. Its title and author come from the PDF's metadata, else the file name and "Unknown author". A library entry has `format: "pdf"` for a PDF; an EPUB's entry has no `format`, so older entries and older clients are unaffected (an older client that moves a PDF's place keeps `format`, since it copies the entry whole; the file-restore, different-edition and removal flows are the same for PDFs and EPUBs, and are tested for both). `pdfjs-dist` (the `legacy` build, pinned) is imported on demand so it only loads on Books pages; in a browser it reads on its own worker (`GlobalWorkerOptions.workerSrc`, set only when `Worker` exists), and without one (tests, Node) it uses its built-in fallback. It takes over the buffer it is given, so `parsePdf()` passes a copy. A PDF is untrusted input: fonts aren't loaded (`disableFontFace`), XFA is off, and text only leaves as plain strings. `src/test/pdf.ts` builds fake text PDFs (`textPdf()`, `pdfFile()`) with standard Helvetica; `gpayPdf.ts` can't be used for this, because its stand-in font only its own reader understands. `PdfError` has four codes: `invalid` (damaged or not a PDF), `scan` (no text anywhere; pages without text are skipped, so a mostly scanned PDF still reads), `encrypted` (pdf.js asks for a password) and `limit` (over `MAX_PDF_PAGES` pages or `MAX_PDF_CHARS` characters; `parsePdf()` takes lower limits as its third argument for tests). A PDF encrypted with only an owner password opens in pdf.js, so it is read; it is not refused. `addBook()` refuses bytes that are neither a PDF nor a zip with `EpubError("invalid")`, and anything over 50 MB before reading it. Reading reports progress and can be stopped: `parsePdf()` takes `onProgress(pagesRead, pages)` (after every page, which also yields to the browser between pages) and an `AbortSignal` (an `AbortError`, nothing added); `addUpload()`/`addBook()` pass them through as `ReadHooks`, and the Books page shows a `<progress>` bar and aborts when it unmounts. pdf.js itself parses on its own worker thread in a browser; the main thread only joins the text, splits sentences and hashes the file. Text cleanup lives in `lib/pdfText.ts` (heuristics; thresholds are constants at its top): `linesOf()` in `pdf.ts` turns pdf.js items into lines with their `y` and height; `stripPageFurniture()` drops bare page numbers and lines (≤ 80 characters, digits ignored) that repeat among a page's first or last 2 lines on at least half the pages (and at least 3), and never on documents of fewer than 3 pages or on pages of fewer than 5 lines; `paragraphsOfPage()` joins lines, starting a paragraph at a gap over 1.6 line heights or where text jumps back up the page, and rejoins a word hyphenated at a line end (the hyphen goes when the next line starts in lower case, so a real compound split over two lines, "well-" "known", loses its hyphen); `joinPages()` carries an open paragraph (not ending in `. ! ? … ” ’ ) ] :`) over the page break. Sentences are split per paragraph. `looksMultiColumn()` guesses columns from where text sits (`spansOf()` in `pdf.ts`): a page counts when a clear strip (≥ 12 points) in its middle 40% is crossed by at most 10% of its text pieces and each side holds ≥ 5 pieces and ≥ 25% of them, and the PDF is flagged when at least 30% of its text pages (≥ 10 pieces) count. It only sets `ParsedBook.warning` (a note the book page shows above the player; text is never reordered). Plan and tickets: `.scratch/books-pdf/` (all done).
- **Books sync** (`lib/booksDoc.ts`, doc key `books`, stored locally as `reel-radar-books`): one item per book, `{ entry, position?, removed?, updatedAt }`, merged three-way by id with the newest change winning. A removal is a marker, never a deletion: it is final (an older or newer copy of the book can't undo it) and it is how other devices learn to delete their file (`purgeRemoved()`). `savePosition()` writes locally after every sentence and does NOT mark the doc dirty; `commitPosition()` does, and is called when playback stops, the chapter changes, and the page is left or hidden (`pushPosition()` also pushes at once). Before this doc existed the library was in `books-library-v1` and `books-position-v1`; `readDoc()` moves those over once. Adding a file for a book that is already in the library (from another device) stores the file under the existing id and keeps its place (`restored`); a catalogue book is matched by `sourceId` when its edition has changed.

Audio streams from archive.org straight to an `<audio>` element, so it costs no function calls. The user picks the recording; never attach one automatically (a title can match the wrong book). The choice is `recording` on the book's item in the `books` doc, with its own `recordingAt` so a choice made on one device and a place saved on another both survive the merge. Which way a book is listened to is per device (`books-mode-v1`).
- **Player** (`lib/player.ts`, `lib/usePlayer.ts`): sentence-at-a-time, validated on Android Chrome (see `.scratch/books/spec.md`). Android sends no word events (highlight per sentence only), its own pause is unreliable (pause = `speechSynthesis.cancel()`, play re-speaks the sentence), and sentences over 1,000 characters fail (`chunkSentence`: cut after a comma, semicolon or colon when one falls past 30% of the limit, otherwise at the last space, otherwise hard; PDF text can be one long unpunctuated run, so this matters there too). Every spoken sentence carries a `runId`; an end event from an older run is ignored. The position is saved to `localStorage` (`books-position-v1`) after every sentence, only once `state.key` matches the loaded chapter. A failed sentence is retried twice (`MAX_RETRIES`), and a chunk that outlasts a time estimate counts as a failure (stall watchdog); the page pauses when `visibilitychange` says hidden, since Android's engine fails in the background. Voice and speed live in `books-voice-v1` and apply from the next sentence. Tests fake `speechSynthesis` and finish each utterance by hand (see `app/books/[id]/page.test.tsx`).
- **Piano** (`/piano`, plan in `.scratch/piano/`: `spec.md`, UI revamp in `revamp-spec.md`): only `lib/pianoMidi.ts` touches Web MIDI (`navigator.requestMIDIAccess({ sysex: false })`); UI reads its snapshot (`unsupported | denied | disconnected | connected`, devices), subscribes with `onNote()` and calls `noteOn`/`noteOff` (on-screen keys, `source: "screen"`) or `play()`. Note events carry the device's own `timeStamp` (performance.now clock); use it for timing scores. Output goes to the keyboard when connected, otherwise `pianoSynth.ts`. `PianoProvider` creates the connection in `useState` and starts it in an effect, so the first render never reads browser state; it also runs `syncPiano()` on open and watches the open keys; `setStaged(true)` (a mounted Stage) hides its app header. Pages re-read local data with `usePianoSync(reload)` so another device's sessions appear. `PianoKeyboard` is the reusable keyboard (`pressed`, `lit`, `fingers`, `low`/`high`, `fill` = keys stretch to the parent's height, `minKey`; scrolls sideways when the range won't fit). Tests use `src/test/midi.ts` (`fakeMidi()`: plug, unplug, noteOn/noteOff with timestamps, `sent()`) and `src/test/audio.ts`. Real hardware is only checked by hand. Timing (`lib/pianoTiming.ts`, all times ms on the `performance.now()` clock, the same as a note event's `time`): `createScheduler({onBeat, clock?})` with `start({bpm, beatsPerBar, countInBars, at?})`, `stop`, `setBpm` (from the next unscheduled beat), `nearest(time)` (nearest non-count-in beat); a 25 ms interval hands out each `Beat` {index, time, bar, beatInBar, accent, countIn} 100 ms ahead and the caller plays it at `beat.time`: `midi.click(accent, at)` sends GM percussion on channel 10 (status 0x99; Hi Wood Block 76 velocity 120 on the accent, Low Wood Block 77 velocity 95 otherwise; one-shots, no note-off) with `at` as the MIDI timestamp, or, with no keyboard, `pianoSynth` schedules a square-wave beep (1600 Hz accent, 1000 Hz) on the audio clock. Tests inject `clock: {now, setInterval, clearInterval}`. Scoring: `scoreHit(hit, expected | expected[], {windowMs = 100, latencyMs})` gives `{grade: early|on|late|missed, offsetMs (negative = early), expected}`; `scoreRun(expected[], hits[], opts)` matches each note to the nearest unused hit within 2.5 x window (else missed) and returns the stray hits as `extra`; `offsetStats` gives mean and spread. Latency: each device has its own input delay, so `reel-radar-piano-timing.latencyMs` (localStorage, not synced, with the last tempo and bar length) is subtracted from hit times: pass `loadLatencyMs()` as `latencyMs` in any scorer. The Metronome's tap-along measures it (average offset of the last 16 hits, "Set from average"). `useMetronome({onBeat, windowMs})` (inside PianoProvider) is the engine and `BeatDisplay`, `TempoControl`, `StartStop`, `BeatsPerBar`, `CountInToggle`, `TapAlong` are its parts; `/piano/metronome` lays them out on a keyboardless Stage (the old `<Metronome>` card is only rendered by its test). Fake MIDI records `sent()` and `sentTimes()` (the timestamp of each send); the fake AudioContext records each voice's `hz` and `startAt`. Drills: a drill is a `DrillDef` (lib/pianoDrill.ts); `DrillRound` judges note-ons (`judge` gets the held set, so chords can return `pending`), picks items by weight (error + half the slow rate over the last ~3 months of records and the round so far, floor 0.1, unseen 1, never the same item twice in a row), counts the first answer only (a miss keeps the item until it is played right), and checks unlock and slow-limit tightening over the last 20 first answers (accuracy >= 90% and median under the limit opens the next group; median under the next step, 2 s to 1.5 s to 1 s, tightens; the window restarts after a change). Timings use the MIDI event time on the `performance.now()` clock; the saved record uses wall time. Rounds with no answers are not saved. Round options: `lengthMs` (default `ROUND_MS` 2 min) and `items` (ids; only open items count, fewer than 3 are padded with the weakest other open items, an empty or non-matching list is ignored). A filtered round never unlocks groups or moves the slow limit. `peek()` returns the next item and the following `next()` makes exactly it current; `previous` is the last item answered right and its time (the stage shows both beside the target). Per-item `ms` (optional, new records only; `ItemTotals.ms`, `Stats.ms`/`msN`): the SUM of reaction times (ms) of the item's correct first answers, so `msN` = attempts - misses of records that carry `ms`; old records lack it and are never counted into an average (`avg = ms / msN`; absent = "no data"). Additive, so the sync union merge and older clients are unaffected. A new drill is a def plus a page that renders `<DrillRunner def blurb />`; props: `lengthMs`, `items`, `onFinish(summary, record, prevAvgMs)` (after the save; prevAvgMs = `lastRoundAvgMs` of the previous round, null = none), `top`, `autoStart` (skip the start screen), `showResults` (false in a session), `backHref`/`backLabel`. Rhythm (`lib/pianoRhythm.ts`, `RhythmRunner.tsx` rendered by `/piano/rhythm`; same `lengthMs`/`onFinish(summary, record)`/`top`/`autoStart`/`showResults` props as DrillRunner): one pattern is not one note-on, so it does not use `DrillRound`; `RhythmRound` keeps the same shapes. Patterns are 8-char eighth-slot strings (`x` note, `-` held, `.` rest) in 5 groups; the learner hears a 1-bar count-in (scheduler `at`, `countInBars: 1`) then plays 2 bars on any key; `round.score(startMs, bpm, hitTimes, loadLatencyMs())` runs `scoreRun`. Rate = on-time notes / (expected + stray hits); pass = rate >= 0.75. Record (`drill: "rhythm"`): one run = one attempt, `misses` = failed runs, `slow` = 0, `avgMs` = mean absolute offset in ms (the log shows it as "Avg error" in ms). Unlock: 5 of the last 6 runs pass. The on-time window is `DrillSettings.slowStep` (saved in `slowSteps.rhythm`) indexing 100/80/60 ms, narrowing when the mean rate of the last 6 runs is >= 0.9; both windows restart after a change. Tempo (default 70) is component state, not saved. The runner guards double scoring with a ref (a tick can fire twice before a re-render). A def may add `caption(item)` (small line above the label) and `setup(item, range)` (finger numbers shown on the keyboard all round, before the hint). Chords (`lib/pianoChordDrill.ts`): correct when the held pitch classes equal the chord's; only the newly pressed note can be a miss (keys left from the last chord aren't), and stale non-chord keys keep the answer pending until released. A def's optional `settle(item, held)` is checked on every note-off, so lifting the last stale key answers the chord (C to Am keeping C and E is the common case). Ids are ASCII (`Bb7`), labels use ♭. Five-finger (`lib/pianoFingerDrill.ts`): positions are tonic + 0 2 4 5 7; RH thumb on tonic at octave 4, LH finger 5 on tonic at octave 3; exact key only; the position's fingers show always, the hint lights only the called key. Songs (`/piano/songs`, `[id]`): a `Song` has notes `{start, dur (beats), pitch, hand "R"|"L", finger 1-5, suggested?}`; built-ins are written in `SONG_DEFS` as two strings (right and left hand) in the notation of `parseHand`: bars split by `|`, tokens by spaces, token = `pitch[:beats][/finger]` (`E4:.5/3`, rest `R:2`, chord `C3+E3+G3:4/5+3+1`, a finger per pitch is required, the first bar may be a pickup, every other bar must add up to `beatsPerBar` and both hands must have the same bars: the library test checks it). Beats are in quarter notes (Für Elise counts eighths as beats). `stepsOf` groups both hands' notes by start beat; a chord is one step. Wait mode (`pianoSongWait.ts`, pure, immutable `WaitState`): expected = the chosen hand(s)' notes of the current step, `press(state, note, held)` is called on every note-on (a key still held from the last step cannot complete a step): not expected = miss (counted, no advance), all expected held = next step, a step with nothing for the player (`expectedNotes` empty) ignores the keyboard and `SongPlayer` moves on after `stepDelayMs` (gap to the next step x `beatMs(bpm, speed)`); the other hand's notes are `autoNotes`, played with `midi.play` when the step is reached, for their length at the same pace. Changing the hand button restarts. `FallingNotes` measures its own box and is passed to the Stage as `above`, in the same scroller and viewBox width as `PianoKeyboard` (`bare`, `keyLayout()`; `tint` colours a lit key): the current step sits on the keys, later steps stand higher by beats, bars say the letter at the foot and the finger in a dot at the head (a short bar: a small raised finger after the letter), so the text reads letter then finger; colours: right hand amber (bar `fill-amber-400`, lit key `fill-amber-300`), left hand sky (`fill-sky-500`, `fill-sky-300`), the app's hand dimmer; pressed keys are brass (`fill-pn-brass`) and drill targets emerald. A finished or stopped run (at least one step played) is saved with `saveSession` as `drill: "songs"`, items `{[songId]: {attempts: 1, misses: wrong keys, slow: 0, avgMs: 0}}`, `durationMs` = wall time of the run; the log counts it in minutes and the recent list but gives it no weekly accuracy table (misses there are counts, not out of attempts). Play-along (`usePlayAlong`, `lib/pianoSongPlay.ts`): a 1-bar count-in of clicks (`createScheduler` with `at`), then the song at the ladder tempo (`ladderTempo`, not the speed slider); the app's hand is sent with `midi.play(note, vel, dur, at)` from the scheduler's `onBeat` (the keyboard gets note-on/off with MIDI timestamps `at` and `at+dur`; the synth fallback uses a timer), clicks through the song only when the "Click during the song" toggle is on. Hits (note-ons from the count-in's last 250 ms) are scored by `scorePlayAlong` with `loadLatencyMs()` and the +-100 ms window; a 50 ms tick colours notes live (`FallingNotes` `at`/`marks`: green on time, violet early, orange late, red missed). After the last note + 300 ms the summary shows on-time %, early/late, missed, mean offset, "You rush in bar N and drag in bar M" (bar mean at least 15 ms off) and stray keys. Saved as `songs` with `misses` = notes not on time, `avgMs` = mean absolute offset; Stop discards a play-along run. Ladders: the tempo ladder starts at ~60% of the song bpm (5s, min 40) and goes +5 after a run with >= 90% on time, capped at the song bpm ("Next run: N BPM"); the hands ladder is R wait, L wait, both wait, both play-along. A finished wait run with <= max(2, 10% of steps) misses completes its step (progress `step` = the next step); both hands at tempo completes (song `mastered`) only with >= 90% on time at the song's full bpm. The page opens on the saved step, highlights it, and "Try next step" switches hands and mode; any combination can still be picked. The songs list shows `progressLine`. Progress is written (and the settings doc queued) only when it changes. Imported songs (MIDI import, `/piano/songs`): `lib/pianoMidiFile.ts` is the pure, hand-written Standard MIDI File reader (formats 0 and 1; format 2 and SMPTE division are refused) and treats the file as untrusted: at most 256 KB (`MAX_MIDI_BYTES`, checked from `File.size` before reading), 5000 notes, 128 tracks, a bounds check on every read, and every loop consumes a byte; problems are a `MidiFileError` with code `invalid | unsupported | too-big | empty` and a user-facing message. Channel 10 is dropped, starts and lengths are quantized to 1/4 beat, the first tempo gives bpm (clamped 40-240), the first time signature gives beatsPerBar in quarter notes (6/8 is 3), leading empty bars are removed. `lib/pianoSongImport.ts`: `planHands()` (two note-bearing tracks, or one track on two channels: higher average pitch is the right hand; otherwise a split pitch, default 60, notes at or above are right; the split is stored in the doc) and `buildImportedSong()` (level 0, `imported: true`, every note `suggested: true`); `lib/pianoFingering.ts` `suggestFingering()` is the rule-based suggester (chords by size: 2 notes 1-5 or 1-3 by interval, 3 notes 1-3-5, 4 notes 1-2-3-5, mirrored 5-3-1 for the left; single-note lines use a five-finger position of 7 semitones chosen from the next 12 notes, finger = `FINGER_AT[distance from the anchor]`, no thumb-under). Storage: one doc per song, `piano-song-<12 hex>` (`SONG_ID`, in `DOC_KEY`), compact `SongDoc` (`notes` as `[start, dur, pitch, hand 0|1, finger]` rows, about 20 bytes a note, capped at `MAX_SONG_DOC_BYTES` 200 KB) that is never edited; `decodeSong()` validates every field and is the only way a stored or synced doc becomes a `Song`. The index is `importedSongs: {[id]: {title, at, removed?}}` in `piano-settings` (union by id, a `removed` marker is final, malformed entries dropped by `cleanImported()`); at most `MAX_IMPORTED` (50) live songs. `/api/sync` has no delete, so `deleteImportedSong()` sets the marker and replaces the doc with the tombstone `{removed: true}` through the normal push (`mergeSongDoc`: removal wins); media-style `deleteDoc` is not reachable for sync docs and no route was added. `pullImportedSongs()` (songs list, on open and on a settings change) fetches only the listed, not-removed docs this device lacks (one read per song per device, none otherwise), and `pullSongDoc(id)` does the same for a direct link; the player page reads the song after the first render (so it never changes hydration) and shows "Loading…" until it has looked. The list shows imported songs under "Your songs" with an "Imported" badge and an in-page delete confirmation; the player header says "Imported" and "fingering suggested". `src/test/midiFile.ts` builds fake MIDI files (`midiFile`, `track`, `on`, `off`, `tempo`, `timeSig`, `note`, ...).
- **Piano practice tools**: Ear training (`/piano/ear`, `lib/pianoEarDrill.ts`) is a plain DrillDef that uses the def's optional `sound(item)` ({groups, gapMs, velocity?}: DrillRunner plays it with `midi.play(..., at)` whenever a new item shows, `round.shownAt` changes, and on **Hear again**), `prompt(item)` (shown large instead of the label, and "?" for Next, so the answer stays hidden; the label names it under Last and in the summary), `leadMs(item)` (taken off the reaction time and the hint delay) and `hintAfterMs: Infinity` (hint only after a miss). `judge` gets a 4th argument `hits` (note-ons since the item showed or was last missed; DrillRound clears it on a miss), which is how a phrase is answered note by note. Evenness of touch (`lib/pianoTouch.ts`): only `source: "keyboard"` note-ons count (screen keys send a fixed velocity); DrillRunner collects the velocity of each right answer for defs with `fingerOf` (five-finger) and passes `touch` to the drill card and as `onFinish`'s 4th argument; SongPlayer in scale mode maps each key to its finger in the chosen hand(s) and shows a Touch block after a run (`TouchBlock` in Results). Bar loops (`lib/pianoLoop.ts`; not offered when `autoStart`, so never in a session): the player runs `sliceSong(song, range)` for wait and play-along, restarts 1.5 s after each finished run until Stop / Stop loop, feeds its own ladder instead of `applyRun` (loop runs are saved as practice but never change song progress), and counts bars in the whole song (`firstBar`), so "Practise bar N" under a rush/drag line opens exactly that bar. Melody + chords songs (`SongDef.chords`, `parseChords`): bars like the melody, tokens `Name[:beats]` sharing the bar evenly, `-`/`N.C.` = rest, a chord repeated over a bar line is held; the left hand gets `chordVoicing` (each tone at its lowest pitch from B2: C = C3 E3 G3, F = C3 F3 A3, G = B2 D3 G3; fingers 5 3 1 / 5 3 2 1); a melody that would hit a chord key is written an octave up (the library test checks no key is in both hands at once). Record and replay (`lib/pianoRecording.ts`): every run's note events are recorded from its start; the last run is saved per device and **Hear your run** replays it with timers (so Stop replay cancels the rest) through `midi.play`, lighting the keys. Milestones (`lib/pianoMilestones.ts`): the home checks `newlyMet` on load, saves new ones, and lists all eight (earned in brass, "New" for those reached this visit).
- **Piano stage, session, results** (`.scratch/piano/revamp-spec.md`): every practice screen (drills, rhythm, songs, scales, exercises, free play, metronome) renders in `<Stage>`: `top` (between back button and connection dot), children (middle), `above` (FallingNotes, may be a function of the range), `notes`/`range` (keyboard range from `keyboardRange`), `follow` (notes to keep in view when the keyboard scrolls sideways), keyboard props, `noKeyboard`, `sheet` (the settings sheet: hands, mode, speed, ladder chips, legend, hint delay; the Settings button shows only when there is a sheet), `backHref`/`backLabel`. The stage owns fullscreen (requested as it opens; Enter/Exit full screen button; fullscreen is kept across consecutive stages, the old one exits only if no new stage mounted by the next tick; leaving fullscreen doesn't stop anything), the orientation lock (tried only in fullscreen, failures ignored), the wake lock (`useWakeLock(true)` while mounted, so no page needs its own; `useMetronome` also holds one while running) and hides the Piano app header. `StageProgress` is the session's bar (one segment per step, width = minutes). Today's practice: Start (TodayCard, calls `unlockAudio()` in the tap) goes to `/piano/practice?start=1` (the step starts at once, then the flag is cleared); each step runs in `practice/StepRunner.tsx` on its own stage with `autoStart`, `showResults={false}` and `lengthMs = minutes`; drill steps pass the step's `items` filter. Song steps use the SongPlayer props `hands`, `mode`, `tempo` (starting values, replacing the saved ladder step), `autoStart`, `onFinish(SongResult)` (fires once per started run, also for Stop; a stopped play-along run is discarded and a stopped wait run with a step played is saved; changing hands or mode mid-run abandons the run without it), `stopRef`; timing rule: after a finished run another run starts until the step's minutes have passed, then the step ends with the last run's card; a **Finish step** button ends it early. After a song run the summary replaces the falling notes. Back = "Pause practice" (state kept, home shows Resume: step N of 3). Finished steps are ordinary drill/song records, so minutes, streak and sync work unchanged. `Results` takes cards (`drill` with summary + prevAvgMs, `rhythm`, `song` with a SongResult; tag = small label) and an optional `noteSpeed`, plus `primary`/`secondary` actions; a drill or song opened from the Library ends on the same screen with its own card, and the note-speed keyboard (`todayNoteSpeed`, the note drill since midnight) shows when notes were played. Slow keys are named as tomorrow's warm-up.

## Testing

- Tests live next to their source as `*.test.ts(x)`. Everything is covered: `lib/`, `types/`, `proxy.ts`, all API routes, the shared components, and **every page** (each `app/**/page.tsx` has a render test, and the planner's Goals, Lists, Review, Stats and Search have their own; the home, layout, search, person and watchlist pages share `app/simple-pages.test.tsx`).
- **Pages need render tests.** A new page, or a new button, filter, form or state on one, gets a test that renders the page and drives it through the UI (click, type, drop) and checks both what's shown and what's saved. Logic in `lib/` still gets its own unit tests.
- Coverage is enforced: `npm run coverage` fails below 97% lines/statements, 95% functions and 90% branches (`vitest.config.mts`). Don't lower the thresholds to get a change through; add the missing tests.
- Page tests run against the real `lib/` code and `localStorage`; only `fetch` is faked. Use `src/test/pages.ts`: `routeFetch({ "/api/x": body | (url, init) => body })` answers by path (`/api/sync` defaults to an empty server), `requests(fetch, path)` lists calls, `seed()`/`stored()` read and write Reel Radar state, and `stubLocation()` replaces `window.location`. Mock `next/navigation` (`usePathname`, `useSearchParams`, `useParams`) in each page test.
- jsdom gaps: there's no `DragEvent`/`PointerEvent`, so set `clientY` and modifier keys on the event yourself (see `dragTo()` in `src/test/planner.tsx`), and dispatch pointer moves as `MouseEvent`s. `Element.scrollTo` and `Notification` need stubs.
- The task list is reordered by a pointer-driven drag handle (`todos/useListReorder.ts`), not HTML5 drag and drop. Tests press the handle with a `pointerdown` `MouseEvent`, move with `pointermove` on `window`, and stub each row's `getBoundingClientRect` because jsdom has no layout (see `swiping and arranging rows` in `todos/page.tasks.test.tsx`).
- Tests run in Node by default. Anything that touches the DOM or `localStorage` starts with `// @vitest-environment jsdom`.
- Shared helpers: `src/test/fixtures.ts` (`mk()` builds a `Title`, `jsonResponse()` builds a fetch response), `src/test/pages.ts` (above), `src/test/planner.tsx` (the planner page tests' helpers: `open()`, `add()`, `todo()`, the fixed day `T`, `FakeNotification`, drag helpers), and `src/test/setup.ts` (React cleanup, lets pending sync work settle, then resets `localStorage`).
- Piano stage tests: `openSettings()` (`src/test/stage.ts`) opens the stage's Settings sheet before a test touches hands, mode, speed or the ladder. jsdom has no fullscreen, orientation lock or ResizeObserver: stub `document.documentElement.requestFullscreen`/`document.exitFullscreen`, `screen.orientation` (`{type, lock}`) and a `ResizeObserver` that reports the size the test gives (see `app/piano/Stage.test.tsx`, `songs/stage.test.tsx`); a refused fullscreen or lock must not break the page. Session tests set the day via fake `Date` and read the `reel-radar-piano-session-*` key.
- Never hit the network: stub `fetch` with `vi.stubGlobal`, and mock `@/lib/tmdb` with `vi.mock`. Sync tests use an in-memory libSQL database in place of `@libsql/client/web`.
- Sync route tests must point `process.cwd()` at a temp dir and re-import the route (see `src/app/api/sync-route.test.ts`), so the real `data/` files are never touched.
- Don't return a value from `beforeEach(() => ...)`. Vitest calls a returned function as cleanup, so `beforeEach(() => mock.mockResolvedValue(x))` ends up calling the mock after every test. Use a braced body.
- When adding a feature, add tests for it in the same change.
- Speed: tests run on 75% of cores (`maxWorkers` in `vitest.config.mts`), so the slowest file sets the run's length. The planner page tests are split by area into `todos/page.test.tsx` (header, top card, attention, day log, adding, tasks), `page.tasks.test.tsx` (details, focus, rows, keys, timeline, day bar, tools, filters) and `page.views.test.tsx` (calendar, plans, links, More, search, reminders); add to the matching one, and split again if one file grows past the others. Under load a state that arrives asynchronously (IndexedDB, sync) can land after a message, so wait with `findBy…` rather than `getBy…` for anything that isn't already on screen, and don't sit through real-time delays (stub the timer).
- Pages sit behind login. To check UI in a browser, set `APP_USERNAME`/`APP_PASSWORD`/`AUTH_SECRET` in `.env.local` and sign in at `/login`. If you couldn't view a page, say so; don't claim it was visually checked.

## Don'ts

- Don't commit secrets, `.env.local`, or `.next/`.
- `data/storage.json` is intentionally tracked in git (it holds the owner's viewing history). Don't delete it, reset it, or overwrite it with test data. The other `data/*.json` files are local dev docs and stay gitignored.
- Don't run the dev server or scripts against the live Turso database to test changes (see "Keep away from live data").
- Don't add dependencies without a clear need. The dependency list is deliberately small.
- Don't send TMDB requests or the API key from client components.

## Money security review

The Money app holds personal financial data and the GitHub repo is public. Whenever you change the Money app or anything its data passes through (`app/money/`, `lib/money.ts`, the statement readers, `api/sync`, `lib/docStore.ts`, `lib/sync.ts`, `proxy.ts`, `lib/auth.ts`, `api/auth/*`, `next.config.mjs`), or propose such a change, check it for security concerns and report the result, even when there are none ("Security: no concerns, because ..."). Check at least:

- **Login gate**: money data is reachable only with a valid session. Every new route or page stays behind `proxy.ts` (watch its `matcher` exclusions and the `/login`, `/api/auth/` bypass), and no server component or route reads money docs without going through it.
- **Encryption at rest**: `money-*` docs are always sealed in `docStore`, with no plain-text path or missing-key fallback (see Sync above). A new money doc key must match the `/^money-/` encryption rule and the `DOC_KEY` allowlist.
- **No leaks**: money data, statement text, UPI ids, names, or amounts never go into logs, error responses, URLs/query strings, analytics, or third-party requests (TMDB included), and never into git: real statements stay in gitignored `data/`, and tests use fake data from `src/test/gpayPdf.ts`.
- **No real data in the repo**: personal names, emails, phone numbers, account numbers and statement rows don't go into code, tests, fixtures or docs. Real names come from `MONEY_MY_NAMES`/`MONEY_FAMILY`; tests use made-up ones.
- **Untrusted input**: imported PDFs and restored backups are untrusted. Validate their shape and size, and render their text as React text only (no `dangerouslySetInnerHTML`, no `eval`, no building HTML from it).
- **Auth and session**: don't weaken the cookie flags (`httpOnly`, `sameSite`, `secure`), the constant-time comparisons, the login delay, or the security headers in `next.config.mjs`. Don't add state-changing `GET` routes.
- **Dependencies**: a new dependency that touches money data needs a clear reason and a check for known vulnerabilities.

If you find a concern, say so before or alongside the change and propose a fix. Don't silently work around it.

## Free-tier usage and performance

The app runs on free or hobby plans (Vercel Hobby, Turso's free plan), so keep usage low without making it slower for the user.

- For every change, consider what it adds: function calls, proxy runs, database reads and writes, TMDB requests, bandwidth, and client bundle size.
- Prefer savings the user doesn't notice: browser and data caching, conditional reads, batched writes, static rendering, and doing work in the browser.
- Don't trade away perceived speed, sync freshness or correctness to save usage unless the owner agrees. Local changes must still feel instant.
- Don't add polling, cron jobs, or per-render or per-keystroke requests without counting their monthly cost.

When a task affects usage or performance, report this before the commit message:

- **Usage:** what changes, with numbers where possible (for example, "+1 read per page open, about 300 a month").
- **Performance:** what the user would notice, or "no noticeable change".
- **Trade-off:** what you chose and why, plus any option you rejected.

If a task affects neither, say so in one line: "Usage and performance: no impact, because ...".

## Finishing a change

- Always end by giving a ready-to-use commit message for the changes made: a short imperative subject line (about 50–72 characters), a blank line, then a few bullet points on what changed and why. Give it even when you weren't asked to commit. Don't commit or push unless asked.
- Anything that depends on the browser (`localStorage`, `Date.now()`/today, `window`) must not change the first render, or hydration fails. Read it in an effect (or after a `mounted` flag) instead.
